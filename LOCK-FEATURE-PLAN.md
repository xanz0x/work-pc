## 1. Суть идеи (как её понял я)

1. **Мастер-пароль ИЛИ PIN** — постоянный, создаётся один раз в Настройках.
2. **Блокировка всего приложения** — без пина не войти (сейф целиком за замком).
3. **Повторный пин на отдельные файлы** — при открытии «запароленного» файла поверх общей разблокировки.
4. **Кнопка блокировки у шестерёнки** (правый верх) — мгновенно закрыть приложение.
5. **Экран блокировки** — полноэкранный ввод пина/пароля в стилистике «Графит».
6. **Автоблокировка** — настраивается: выкл / 5 / 10 / 15 / 30 минут.

**Текущее состояние защиты в прототипе (важно понимать):**
- Стикеры уже имеют `locked: boolean + secret: string | null` (lib/notes.ts), но секрет хранится **в открытом виде** в localStorage, а разблокировка — просто клик «Ввести ключ» с проверкой строки.
- Бейджи «AES-256», «Зашифровано» — декоративные, реального шифрования нет.
- Этот план превращает декорацию в настоящую защиту (WebCrypto), не ломая демо-данные.

## 2. Архитектурное решение

### 2.1 Два уровня ключа

| Уровень | Что защищает | Когда спрашивается |
|---|---|---|
| **Уровень A: Мастер-ключ** (PIN 4–8 цифр или пароль ≥8 симв.) | вход в приложение целиком | при запуске, по кнопке-замку, по автоблокировке |
| **Уровень B: Файловый ключ** (пароль на файл/стикер) | содержимое конкретного объекта | при каждом открытии файла (после уровня A) |

Правило UX: файловый ключ НЕ наследуется от мастер-ключа (осознанная безопасность:
кто подсмотрел пин входа — всё равно не откроет финансовые документы).

### 2.2 Криптография (WebCrypto, без библиотек)

Новый модуль `lib/crypto-vault.ts`:

```
deriveMasterKey(secret, salt):
  PBKDF2(SHA-256, 310_000 итераций, salt 16B) → AES-GCM key 256
  (OWASP-рекомендация для PBKDF2-HMAC-SHA256)

setMasterSecret(secret):
  salt = random(16)
  verifier = AES-GCM.encrypt(key, "workflow-lock-v1")   // проверка при разблокировке
  store: { v:1, salt_b64, verifier_b64, iv_b64, createdAt }

verifyMasterSecret(secret): расшифровать verifier → совпало/нет

encryptSecret(fileId, plaintext):
  key = deriveFileKey(masterSecret?, fileIdSalt)  // см. п.4 — почему нужен мастер
  AES-GCM.encrypt → { ct_b64, iv_b64 } в поле secret файла

unlockAttempt(): счётчик неудач → задержка 1s→2s→4s… (макс 30s), лог в ленту событий сейфа
```

Всё нативное, работает в браузере, zero-dependency. Fallback: если WebCrypto недоступен
(нестандартный браузер) — приложение работает без блокировки, показывая баннер в настройках.

### 2.3 Хранение (localStorage, ключи с префиксом)

```
wf.lock.config    → { enabled, method:'pin'|'password', autoLockMin:number|0, createdAt }
wf.lock.state     → { salt, verifier, iv, failCount, lastFailAt }
wf.vault.keys.<id> → { ct, iv, salt }   // зашифрованные секреты файлов/стикеров
wf.session.unlock → { until: timestamp } // память сессии «разблокировано до…»
```

Существующие `secret: string|null` у заметок мигрируют: при первом включении
защиты старые открытые секреты шифруются, поле становится opaque (`ct:iv`).

### 2.4 Состояние приложения (vault-store.tsx)

Новые поля в VaultState:
```ts
lock: {
  status: 'off' | 'locked' | 'unlocked',
  method: 'pin' | 'password' | null,
  autoLockMin: number,        // 0 = никогда
  lastActivityAt: number,
}
fileKeys: Record<id, { hasKey: boolean }>  // факт наличия ключа (без самого ключа!)
```

Новые действия: `setupLock()`, `lockNow()`, `unlock(secret)` → bool,
`setAutoLock(min)`, `touch()` (любое действие пользователя обновляет активность),
`setFileKey(id, password)` / `openWithKey(id, password)` → bool.

Автоблокировка: таймер в app-shell (setInterval 5s): если `autoLockMin > 0`
и `now - lastActivityAt > min*60_000` → `lockNow()`. Активность: click/keydown/pointermove
(пассивные слушатели на window, throttle 10s).

## 4. Критический момент: файловые ключи vs мастер-ключ

Проблема: если файловый ключ шифруется мастер-ключом — при сбросе мастера рушатся все файловые ключи.
Если файловый ключ существует сам по себе — его нельзя восстановить никогда.

**Решение (принято):** файловый пароль оборачивается мастер-ключом:
`wrappedFileKey = AES-GCM(masterKey, filePassword-derived-key)`.
- Открытие файла: unlock(app) → derive master → unwrap fileKey → verify паролем файла.
- Смена мастера: пере-wrapped всех файловых ключей (быстро, без знания старых паролей файлов).
- Забыл файловый пароль → данные этого файла недоступны (честно пишем в UI).
- Забыл мастер → кнопка сброса: стирает lock.state И ВСЕ wrappedFileKey
  (файлы остаются, их ключи — нет; явное предупреждение при создании).

## 6. Риски и честные ограничения (прописать в UI!)

- Это браузерный прототип: localStorage можно открыть DevTools. Реальная защита
  секретов такой схемы — от «подошёл к чужому компьютеру», не от хакера с доступом к диску.
  Формулировка для настроек: «Ключи хранятся на этом устройстве».
- PBKDF2 310k итераций на слабом ПК ≈ 0.3–1s задержка при разблокировке — это норма, показать спиннер.
- Потеря мастера без запаса = потеря файловых ключей (двойное подтверждение при создании).
- Автозаполнение браузера может предлагать сохранить пин — поле пометить autocomplete="off".

## 10. Аудит логических цепочек v2 (2026-08-26, после глубокого прохода по коду)

Пройден весь путь данных: usePersistedState → vault-store → экраны → поиск → карта → чат.
Ниже найденные дыры исходного плана и их закрытие. Эти пункты ОБЯЗАТЕЛЬНЫ к исполнению.

### 10.1 Гонка гидратации: «замок мигнёт открытым» ❌→✅

**Цепочка:** `usePersistedState` рендерит default-значение до эффекта чтения localStorage
(hydrated=false). Если lock.config читать этим хуком, первый кадр увидит `enabled:false`
→ на ~1 кадр покажется контент приложения, потом резко встанет замок.

**Решение:** конфиг замка читается СИНХРОННО до первого рендера — отдельный модуль
`lib/lock-store.ts` с функцией `readLockBootstrap(): 'off'|'locked'`, вызываемой один раз
в module-scope (localStorage синхронный). App-shell стартует сразу из этого состояния;
экран блокировки рендерится ПЕРВЫМ кадром. Никаких `useState(false)` + useEffect для замка.

### 10.2 Утечка через поиск ❌→✅

**Цепочка:** `searchAll()` ищет по `f.desc` ВСЕХ файлов безусловно и показывает заголовки
в дропдауне поиска над любым экраном. Заблокированное приложение не показало бы UI,
но файловые ключи (уровень B): заблокированный ФАЙЛ всплывает в поиске с desc
«Договор аренды… подписан 12 февраля» — содержимое утекает мимо пина.

**Решение:** в searchAll добавить параметр `redactIds: Set<string>` (id под файловым ключом,
не разблокированные в этой сессии). Для них: score считается только по имени файла,
desc заменяется на «Под ключом», hit получает флаг `locked:true`; инспектор и карта
показывают красакт-представление. Тот же redact применяется в:
- inline-hits дропа поиска (app-shell)
- retrieval-trace чата (источники)
- узлах карты (label остаётся = имя файла; tooltip/desc — красакт)

### 10.3 Чат цитирует защищённое ❌→✅

**Цепочка:** source-desk/retrieval-trace показывают источники с desc; fake-stream
«отвечает» по содержимому. Если источник под ключом — его desc нельзя ни показывать,
ни отдавать модели.

**Решение:** при сборке контекста ответа исключить redactIds из источников; вместо него
в trace попадает строка «Источник под ключом — откройте файл». Это же правило пишем
в ленту: «ИИ не имеет доступа к объектам под файловым ключом».

### 10.4 Карта помнит фокус ❌→✅

**Цепочка:** `openOnMap/openFile/openNote` сохраняют focus id; после блокировки и
разблокировки другим человеком screen-map может отрисовать выбранный ранее защищённый узел.

**Решение:** lockNow() очищает fileFocus/noteFocus/nodeFocus/clusterFocus + sel в библиотеке.
После unlock пользователь начинает с чистого состояния («Всё»).

### 10.5 Сессия «разблокировано навсегда» ❌→✅

**Цепочка:** план v1 хранил `wf.session.unlock.until` в localStorage — но localStorage
переживает закрытие вкладки. Открыл утром — замок «помнит» вчера.

**Решение:** unlock-факт живёт ТОЛЬКО в памяти (React state / sessionStorage как
опция «не спрашивать при перезагрузке вкладки»). По умолчанию: каждая новая вкладка =
новый ввод пина. Автолок-таймер тоже в памяти, сбрасывается при lockNow().

### 10.6 Демо-стикеры принимают любой пароль ❌→✅

**Цепочка:** сейчас submitKey() принимает ЛЮБОЙ непустой ключ для демо-стикеров
(`note.secret && note.secret !== val` — если secret null, проходит всё). При переезде
на crypto это станет дырой: стикер «под ключом» без ct открывается чем угодно.

**Решение:** этап 5 шифрует ВСЕ существующие locked-стикеры при включении замка
(одноразовая миграция: старый plaintext secret → AES-GCM ct, поле становится opaque).
После миграции проверка только криптографическая: расшифровалось верификатором — открыто,
нет — отказ. Правило: `locked=true ⇒ ct существует`, инвариант проверяется при загрузке.

### 10.7 Смена PIN vs смена мастер-пароля — разные потоки ✅

PIN и пароль — два method'а одного мастера. Смена метода = полный re-setup:
старый ключ подтверждается → новый создаётся → wrappedFileKey пере-wrapped →
сессия остаётся разблокированной. Отдельная ветка «Забыл мастер» описана в п.4.

### 10.8 Таймер автолока против PBKDF2 ❌→✅

**Цепочка:** derive занимает 0.3–1s; если запускать derive на каждый тик проверки
или повторный ввод во время delay анти-брутфорса — UX рассыпается.

**Решение:** deriveMasterKey вызывается ровно один раз за попытку unlock;
повторные клики кнопки игнорируются пока идёт derivation (busy-флаг);
анти-брутфорс задержка отсчитывается ПОСЛЕ завершения неудачной попытки;
кэшировать master key в памяти ЗАПРЕЩЕНО после lockNow() (обнулять ссылку).

### 10.9 Вкладки синхронны между собой ❌→✅

**Цепочка:** две вкладки одного приложения: в одной сняли замок, в другой он ещё стоит
(или наоборот) — состояние расходится, localStorage гонки.

**Решение:** событие `storage` слушается в app-shell: изменение wf.lock.config/wf.lock.state
в любой вкладке приводит обе к одному статусу (locked побеждает). Разблокировка в одной
вкладке НЕ разблокирует вторую (unlock-факт в памяти вкладки), но lockNow() закрывает все.

### 10.10 Ctrl+L конфликтует с браузером ⚠️

Chrome: Ctrl+L — фокус в адресную строку. Перехватить можно, но это ломает привычку юзера.

**Решение:** основной хоткей — **Ctrl+Shift+L**, Ctrl+L не трогаем. Кнопка-замок остаётся
главным путём (она рядом с шестерёнкой, как задумано).

### 10.11 Экран блокировки ≠ белый экран при SSR ❌→✅

**Цепочка:** Next SSR отдаёт HTML до знания localStorage; если рендерить lock по client-state,
первая отрисовка после гидратации может прыгнуть.

**Решение:** bootstrap-скрипт в layout.tsx (inline, до гидратации): читает wf.lock.config,
ставит класс `lock-pending` на <html> → CSS мгновенно скрывает app-контент за
заглушкой «…». React при монтировании подтверждает или снимает класс. Мигания нет.

### 10.12 Инварианты целостности (самопроверка при старте)

lock-store.ts экспортирует `auditLockState()`: выполняется после гидратации:
- locked=true у заметки ⇒ есть ct (иначе: снять locked + событие в ленту)
- lock.enabled=true ⇒ verifier расшифровывается текущим мастером при следующем unlock
- wrappedFileKey без родительского lock.state ⇒ пометить объекты «ключ недоступен»
  (честный экран «Сбросьте пароль объекта» вместо вечной ошибки)

### 10.13 Что остаётся честными ограничениями (не чиним)

- DevTools открывают localStorage → защита от чужих глаз/рук, не от форензики. Формулировка в UI.
- sessionStorage-опция «держать открытым в этой вкладке» — по умолчанию ВЫКЛЮЧЕНА.

## 11. Итоговые границы (без изменений)

- Не переносим данные в IndexedDB, не меняем схему демо-файлов.
- Не вводим аккаунты/облако/синхронизацию ключей — локальность принципиальна.
- Не ломаем существующие сценарии доски плиток и карты — lock-слой живёт ПОВЕРХ shell.
- Хоткей блокировки — Ctrl+Shift+L, НЕ Ctrl+L (конфликт с браузером, п.10.10).
